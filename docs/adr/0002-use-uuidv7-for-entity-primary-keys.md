# ADR 0001: Use UUIDv7 for Entity Primary Keys

* **Status:** Accepted
* **Date:** 2024-12-17
* **Tags:** PostgreSQL, Database, Primary Keys

## Context

We need a robust strategy for generating primary keys for our domain entities.

* Using traditional auto-incrementing integers (`BIGINT`) exposes domain logic and creates bottlenecks in distributed
  systems where multiple instances need to generate IDs concurrently.
* Using standard UUIDv4 solves the distributed generation problem but causes massive database performance degradation.
  Because UUIDv4 is entirely random, every new insert forces the PostgreSQL B-Tree index to rebalance, resulting in
  severe page fragmentation and exponentially slower write speeds at scale.

## Decision

We will use **UUIDv7 (RFC 9562)** for all entity primary keys.

## Consequences

### Positive

* **B-Tree Optimization (Time-Ordered):** UUIDv7 includes a millisecond-precision timestamp at the beginning of the
  string. New records are always appended sequentially in the database index, keeping the B-Tree healthy and insert
  speeds incredibly fast.
* **Security & Distributed Safe:** They do not expose domain logic and can be safely generated by the Java Spring Boot
  application before hitting the database.
* **Embedded Data:** We can extract the exact creation timestamp directly from the ID without querying a separate
  `created_at` column.
* **Natural Pagination:** Because they are time-ordered, they serve as perfect natural cursors for high-speed
  Keyset/Cursor pagination.

### Negative / Risks

* **Storage Size:** UUIDs consume 128 bits compared to a 64-bit `BIGINT`, resulting in slightly larger table and index
  sizes.
* **Readability:** UUIDs are harder for developers to read or memorize during debugging compared to short sequential
  numbers.
* **Timing Leakage:** (Mitigated in ADR 0002) Because they contain timestamps, exposing them directly in an API leaks
  the exact millisecond a record was created.
